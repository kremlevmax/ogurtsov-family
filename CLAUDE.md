# CLAUDE.md — семейный генеалогический сайт

## 1. Назначение файла

Этот файл задает постоянные правила для Claude Code при работе с репозиторием. Он имеет приоритет над случайными предположениями агента. Если новый запрос пользователя противоречит этому файлу, сначала укажи противоречие и следуй самому свежему явному решению пользователя.

Рабочее название проекта: **Семейное дерево Огурцовых**.

Технический slug: `ogurtsov-family`.

Интерфейс, документация для владельца и пользовательские сообщения должны быть на русском языке. Имена переменных, функций, файлов, таблиц и комментарии, где они полезны разработчикам, должны быть на английском.

## 2. Главная цель продукта

Создать и опубликовать публичный генеалогический сайт одной большой семьи. Посетитель видит интерактивное семейное дерево, может найти человека и открыть подробную информацию. Только два заранее созданных пользователя — владелец и его мама — могут входить и редактировать данные.

Проект личный и некоммерческий. Приоритеты в таком порядке:

1. сохранность семейных данных;
2. простота использования для человека без технической подготовки;
3. корректность родственных связей;
4. безопасность;
5. стабильная работа на телефоне и компьютере;
6. бесплатная или почти бесплатная эксплуатация;
7. переносимость данных между провайдерами;
8. визуальная выразительность.

## 3. Подтвержденные требования

### 3.1 Публичность

- Весь опубликованный контент доступен без входа.
- Публичные страницы разрешено индексировать Google и Bing.
- Страницы входа и редакторские маршруты должны иметь `noindex`.
- Документы разрешено свободно скачивать всем посетителям.
- PDF не нужно показывать встроенным просмотрщиком; достаточно понятной кнопки скачивания.

### 3.2 Редакторы

- Редактируют только два заранее созданных пользователя.
- Оба входят по email и паролю.
- Публичной регистрации нет.
- Оба имеют одинаковые права редактирования контента.
- Изменения публикуются сразу после сохранения.
- Модерация, черновики, комментарии, уведомления и история версий не нужны.
- Храни `created_at`, `updated_at`, `created_by` и `updated_by` для диагностики, но не создавай полноценную систему ревизий.

### 3.3 Язык и имена

- Интерфейс только на русском языке.
- Контент только на русском языке.
- Не создавай многоязычную архитектуру в первой версии.
- Альтернативные имена на других языках не нужны.
- Для человека поддерживаются как минимум:
  - имя;
  - отчество или второе имя, необязательно;
  - фамилия;
  - девичья фамилия, необязательно;
  - вычисляемое или явно заданное полное отображаемое имя.
- Поиск должен находить по имени, фамилии и девичьей фамилии без учета регистра.

### 3.4 Карточка человека

Поддерживаются поля:

- полное имя;
- дата рождения;
- место рождения;
- дата смерти;
- место смерти;
- родители;
- супруги и партнеры;
- дети;
- профессия;
- образование;
- краткая биография;
- фотографии;
- документы и другие файлы.

Допускаются неизвестные и неточные сведения:

- неизвестная дата;
- только год;
- месяц и год;
- приблизительная дата;
- диапазон дат;
- предположительное место;
- текстовое пояснение к неточности.

Не делай систему источников для каждого факта. У фотографии и файла должны быть собственные текстовые пояснения.

### 3.5 Родственные связи

Поддерживаются:

- биологические родители и дети;
- усыновители и усыновленные дети;
- приемные родители;
- опекуны;
- супруги;
- несколько браков;
- бывшие супруги и разводы;
- партнерство без официального брака;
- неизвестный родитель;
- сводные братья и сестры как производная общих родителей.

Не храни «брат/сестра» отдельной ручной связью, если ее можно надежно вычислить через родителей. Это предотвращает противоречия.

Для неизвестного родителя разрешено создавать специальную placeholder-запись, например «Неизвестный отец», с `is_placeholder = true`.

### 3.6 Дерево

- На главной странице сразу показано одно большое семейное дерево.
- Предки располагаются сверху, потомки снизу.
- Дерево поддерживает zoom, pan мышью и пальцем, fit-to-view и поиск.
- Узлы не должны свободно перемещаться и сохранять случайные координаты пользователя.
- Нажатие на узел:
  1. открывает подробную панель справа на широком экране;
  2. обновляет URL;
  3. позволяет открыть отдельную страницу человека.
- На телефоне подробности открываются как полноэкранный sheet/page, а не как узкая правая панель.
- Ссылка с выбранным человеком должна восстанавливать открытое состояние после загрузки страницы.
- В узле дерева показывай портрет или инициалы, полное имя и годы жизни, если они известны.
- Авторизованный редактор видит быстрые действия:
  - «Добавить мать»;
  - «Добавить отца»;
  - «Добавить родителя»;
  - «Добавить супруга/партнера»;
  - «Добавить ребенка»;
  - «Редактировать».

### 3.7 Фотографии и файлы

- Один объект может быть связан с несколькими людьми.
- Максимальный размер одного файла: `100 MiB` (`104857600` bytes).
- Ожидаемый суммарный объем: до 5 ГБ.
- Для фотографии поддерживаются:
  - название;
  - подпись/описание;
  - дата или приблизительная дата, необязательно;
  - место, необязательно;
  - автор, владелец оригинала или источник, необязательно;
  - связанные люди;
  - признак фотографии профиля;
  - порядок отображения.
- Для документа или иного файла поддерживаются:
  - название;
  - пояснение;
  - дата, необязательно;
  - связанные люди;
  - исходное имя файла;
  - тип, размер и дата загрузки.
- Документы скачиваются, а не встраиваются в страницу.
- Фотографии показываются галереей с полноэкранным просмотром.

### 3.8 Допустимые типы файлов

Пользователь просил «любые файлы», но нельзя разрешать опасные исполняемые и активные веб-форматы. Используй широкую безопасную allowlist и проверяй одновременно расширение, заявленный MIME и фактический тип, когда это практически возможно.

Разрешенные группы:

- изображения: JPEG, PNG, WebP, AVIF, GIF;
- сканы, доступные только для скачивания: TIFF;
- документы: PDF, TXT, RTF, CSV;
- офисные документы: DOC, DOCX, XLS, XLSX, PPT, PPTX, ODT, ODS, ODP;
- аудио: MP3, M4A, AAC, WAV, FLAC, OGG;
- видео: MP4, MOV, M4V, WebM;
- архивы: ZIP, 7Z, TAR, GZ.

Запрещай как минимум:

- HTML, HTM, SVG;
- JavaScript и TypeScript;
- EXE, MSI, DLL, APP, DMG, PKG;
- BAT, CMD, PS1, SH, ZSH;
- JAR и другие исполняемые контейнеры;
- файлы с двойным опасным расширением;
- файл, если тип невозможно безопасно определить.

Не полагайся только на клиентскую проверку.

### 3.9 Места и карта

- Место рождения и смерти может быть простым текстом.
- Дополнительно место может ссылаться на запись `places` с координатами.
- Если координаты есть, в карточке человека можно показать небольшую карту.
- Отдельная глобальная карта не нужна.
- Платный geocoding API не использовать.
- Редактор должен иметь возможность ввести название места и при желании выбрать точку вручную на карте.

### 3.10 Экспорт и резервные копии

- Данные не должны быть заперты у одного провайдера.
- Реализуй локальный экспорт всех прикладных таблиц в JSON и CSV.
- Реализуй локальное скачивание всех объектов R2 с manifest-файлом и checksum, где это разумно.
- Добавь команду `npm run backup:local`.
- Не записывай секреты в backup.
- Добавь понятную инструкцию восстановления в `docs/BACKUP_AND_RESTORE.md`.
- GEDCOM-экспорт желателен после готовности основной версии. Реализуй совместимый базовый экспорт людей, родителей, супругов, рождения и смерти; не задерживай им основной MVP.
- Репозиторий с SQL-миграциями сам является частью стратегии переносимости.

- приватные семейные разделы;
- публичную регистрацию;

- черновики и автосохранение черновиков;

- OCR;
- встроенный просмотр PDF;
- AI-функции;
- платную аналитику;
- сложную CMS поверх приложения.

## 5. Основной стек

Не меняй стек без явного согласия пользователя.

### 5.1 Приложение

- Next.js 16, App Router.
- React и версии зависимостей, совместимые с зафиксированной версией Next.js.
- TypeScript `strict: true`.
- npm и lockfile `package-lock.json`.
- Tailwind CSS.
- Локальные UI-компоненты в стиле shadcn/ui; не добавляй огромную библиотеку компонентов целиком.
- Zod для валидации данных.
- React Hook Form для сложных редакторских форм.
- `date-fns` только если он действительно упрощает работу с датами.
- `lucide-react` для иконок.

### 5.2 Дерево

- `@xyflow/react` для интерактивного canvas.
- `elkjs` для стабильной top-to-bottom layered раскладки.
- Строй промежуточные family-unit nodes для пар и их детей, чтобы уменьшить пересечения линий.
- Скрытые layout nodes не должны быть доступны как реальные люди.
- Код преобразования доменной модели в граф должен быть чистой тестируемой функцией.

### 5.3 База и вход

- Supabase Postgres.
- Supabase Auth с email/password.
- `@supabase/supabase-js` и `@supabase/ssr`.
- SQL-миграции находятся в `supabase/migrations/`.
- TypeScript-типы базы генерируются и хранятся в репозитории.
- Используй Row Level Security.
- Публичный anonymous пользователь имеет только SELECT к опубликованным, не удаленным данным.
- Пользователь может писать только если его `auth.uid()` присутствует в таблице `editors`.
- Не используй service-role key в браузере.
- Не полагайся только на скрытие кнопок в UI: каждая операция записи проверяется сервером и RLS.

### 5.4 Файлы

- Cloudflare R2 Standard storage.
- Не используй Supabase Storage для основных файлов.
- Создавай presigned PUT URL только после серверной проверки активной сессии редактора.
- Загружай файл напрямую из браузера в R2, не проксируй 100 МБ через сервер Next.js.
- Presigned URL должен быть короткоживущим и ограниченным одним object key и одним Content-Type.
- После загрузки выполняй finalize-запрос: сервер делает HEAD объекта, проверяет размер и metadata, после чего создает запись в базе.
- Если проверка не прошла, объект удаляется или помечается для очистки.
- Object keys должны быть UUID-based; никогда не доверяй исходному имени файла как пути.
- Исходное имя сохраняй только как metadata в базе.
- Для публичного чтения используй отдельный минимальный Cloudflare Worker с R2 binding. Он должен поддерживать GET/HEAD, cache headers, range requests, безопасный `Content-Type` и `Content-Disposition`.
- Для изображений допускается inline-отдача. Для документов и иных файлов кнопка скачивания должна принудительно задавать attachment.

### 5.5 Развертывание

- Основное приложение: Vercel Hobby как личный некоммерческий проект.
- База и Auth: Supabase Free на первом этапе.
- Файлы: Cloudflare R2 Free allowance.
- Публичный media endpoint: Cloudflare Worker на `workers.dev` или пользовательском домене.
- До покупки домена используй нейтральные environment variables и не hardcode URL.
- Предварительный Vercel project slug: `ogurtsov-family`.
- Возможный будущий домен: вариант с `ogurtsov`; окончательный домен пока не выбран.
- В `README.md` и deployment guide объясни, что бесплатный Supabase-проект может приостанавливаться при низкой активности и что его нужно восстановить через dashboard; не создавай искусственный keepalive в обход правил сервиса.
- Объясни, что для включения R2 Cloudflare может потребовать активацию billing, даже если фактическое использование остается внутри бесплатного allowance. Не создавай ресурс и не вводи платежные данные за пользователя.

## 7. Модель данных

Окончательная SQL-схема может быть уточнена миграциями, но должна сохранять следующие сущности и свойства.

### 7.1 `editors`

- `user_id uuid primary key` → `auth.users.id`;
- `display_name text`;
- `created_at timestamptz`.

Оба пользователя имеют одинаковое право редактирования.

### 7.2 `people`

Рекомендуемые поля:

- `id uuid primary key`;
- `first_name text`;
- `middle_name text null`;
- `last_name text null`;
- `maiden_name text null`;
- `display_name text`;
- `is_placeholder boolean default false`;
- `birth_date_precision`;
- `birth_date_start date null`;
- `birth_date_end date null`;
- `birth_date_text text null`;
- `birth_place_id uuid null`;
- `death_date_precision`;
- `death_date_start date null`;
- `death_date_end date null`;
- `death_date_text text null`;
- `death_place_id uuid null`;
- `profession text null`;
- `education text null`;
- `short_bio text null`;
- `created_at`, `updated_at`;
- `created_by`, `updated_by`;
- `deleted_at timestamptz null`.

Правила:

- `display_name` обязателен даже для placeholder.
- Для точной даты `start = end`.
- Для года используй границы года или отдельную precision-логику, но форматирование должно быть однозначным.
- Не выводи ложную точность.
- Удаление по умолчанию мягкое через `deleted_at`; полноценной истории версий нет.

### 7.3 `places`

- `id uuid`;
- `name text`;
- `region text null`;
- `country text null`;
- `latitude numeric null`;
- `longitude numeric null`;
- `is_approximate boolean default false`;
- `note text null`;
- timestamps.

### 7.4 `relationships`

- `id uuid`;
- `from_person_id uuid`;
- `to_person_id uuid`;
- `relationship_type` enum/check constraint;
- `parent_role` nullable: `mother`, `father`, `parent`;
- даты начала и окончания с тем же подходом к precision;
- `note text null`;
- timestamps;
- `deleted_at`.

Типы как минимум:

- `biological_parent`;
- `adoptive_parent`;
- `foster_parent`;
- `guardian`;
- `spouse`;
- `former_spouse`;
- `partner`.

Направление parent-типа: `from_person_id` — родитель, `to_person_id` — ребенок.

Для симметричных связей обеспечь канонический порядок пары или уникальный индекс, чтобы не появлялись дубликаты A–B и B–A.

Не допускай:

- связь человека с самим собой;
- явные дубликаты;
- очевидный цикл «человек является собственным предком»;
- удаление человека без понятного предупреждения о зависимых связях.

Сложные случаи кровного родства могут образовывать циклы в общем графе; layout-код не должен зависать.

### 7.5 `media`

- `id uuid`;
- `kind`: `photo`, `document`, `audio`, `video`, `archive`, `other`;
- `title text`;
- `caption text null`;
- `source_or_owner text null`;
- необязательная дата/precision;
- `place_id uuid null`;
- `object_key text unique`;
- `original_filename text`;
- `mime_type text`;
- `extension text`;
- `size_bytes bigint`;
- `sha256 text null`;
- `width integer null`;
- `height integer null`;
- timestamps, author fields;
- `deleted_at`.

### 7.6 `person_media`

- `person_id uuid`;
- `media_id uuid`;
- `is_profile boolean default false`;
- `sort_order integer default 0`;
- composite unique key.

На одного человека должна приходиться не более одной активной profile-фотографии. Обеспечь это транзакционно или индексом, если возможно.

### 7.7 `site_settings`

Минимально:

- singleton key;
- `site_title`;
- `root_person_id uuid null`;
- timestamps.

### 7.8 `pending_uploads`

Используй временную запись для безопасного двухэтапного upload flow:

- editor id;
- object key;
- expected mime;
- expected size;
- expiry;
- status;
- timestamps.

Просроченные незавершенные uploads должны очищаться безопасным скриптом.

## 8. Поиск

- Поиск на главной странице виден сразу.
- Ищи по `first_name`, `middle_name`, `last_name`, `maiden_name`, `display_name`.
- Поиск регистронезависимый.
- Нормализуй повторные пробелы и букву `ё/е` для пользовательского удобства, не меняя сохраненное имя.
- Для небольшого дерева достаточно indexed `ILIKE`/trigram-поиска.
- Добавь индексы, не делай полный scan при каждом символе.
- Клиент использует debounce.
- Результат поиска позволяет:
  - открыть карточку;
  - центрировать и подсветить узел в дереве;
  - перейти на страницу человека.

## 9. URL и маршрутизация

Целевое поведение:

- `/` — дерево и поиск;
- `/?person=<uuid>` — дерево с открытой подробной панелью;
- `/people/<uuid>` — отдельная индексируемая страница человека;
- `/login` — вход редакторов;
- `/edit/people/<uuid>` — редакторская форма;
- API uploads — только для авторизованных редакторов.

Допускается позднее перейти на человекочитаемые slug, но UUID гарантирует уникальность и не ломается при смене фамилии.

## 13. Безопасность

Обязательные правила:

- Никогда не коммить `.env*`, кроме `.env.example`.
- Никогда не выводи secret/service-role/R2 secret в логи или клиентский bundle.
- Проверяй authorization в Server Action/Route Handler и RLS.
- Route Handlers считать публичными API endpoints.
- Валидация Zod выполняется на сервере, даже если есть клиентская валидация.
- Ограничивай rate для login и upload-presign, насколько позволяет бесплатный стек.
- CSRF учитывай для cookie-authenticated mutations.
- Ставь security headers: CSP, frame ancestors, referrer policy, nosniff и разумные permissions policy.
- Санитизируй имена скачиваемых файлов в `Content-Disposition`.
- Не допускай path traversal.
- Не принимай object key с клиента.
- Не выполняй SQL из пользовательского текста.
- Не используй `dangerouslySetInnerHTML` для семейного контента.
- Не делай CORS `*` для upload PUT; разрешай только локальный origin и production origin.
- Секретные server modules помечай и импортируй только на сервере.
- Удаление R2-объекта и DB-записи должно быть согласованным и восстановимым настолько, насколько разумно.

Поскольку весь контент публичный, не создавай ложного ощущения конфиденциальности. В README явно укажи, что загруженные данные и документы доступны любому посетителю и поисковикам.

## 17. Работа с базой и миграциями

- Любое изменение schema оформляется новой миграцией.
- Не редактируй уже примененную production migration задним числом.
- Migration должна быть повторяемой там, где это возможно.
- Добавляй indexes и constraints вместе с таблицами.
- RLS policies являются частью migrations.
- Seed не должен содержать реальные семейные данные.
- Перед потенциально разрушительной migration подготовь backup instruction и запроси явное разрешение.
- Не выполняй `db reset`, `drop schema`, массовый delete или remote migration без явного согласия пользователя.

## 18. Резервное копирование

`npm run backup:local` должен:

1. требовать явно указанную локальную папку или использовать безопасную папку по умолчанию;
2. создавать timestamped directory;
3. экспортировать прикладные таблицы в JSON;
4. дополнительно создавать удобные CSV для людей, связей, мест и media metadata;
5. скачивать R2 objects, сохраняя структуру object keys;
6. создавать `manifest.json` с версиями schema, количеством записей, размером и checksum;
7. не перезаписывать существующий backup;
8. завершаться non-zero code при неполной копии;
9. печатать понятный итог по-русски;
10. никогда не включать secrets.

Создай также `npm run backup:verify` для проверки manifest и файлов.

Позднее можно добавить пример macOS `launchd`, но не активируй его автоматически.

## 23. Definition of Done для MVP

MVP готов только когда:

- публичный посетитель видит дерево без входа;
- поиск находит имя, фамилию и девичью фамилию;
- click/tap открывает details и меняет URL;
- отдельная страница человека работает;
- оба editor account входят по email/password;
- editor может создать, изменить и безопасно удалить/восстановить человека;
- editor может создавать все согласованные типы связей;
- editor может добавлять родственника прямо из дерева;
- approximate dates не превращаются в точные;
- фото и файлы до 100 MiB загружаются напрямую в R2;
- опасные типы отклоняются;
- один media object связывается с несколькими людьми;
- документы публично скачиваются;
- mobile UI пригоден для использования;
- RLS и server authorization закрывают запись для анонимных пользователей;
- lint, typecheck, tests и build проходят;
- есть рабочий локальный backup;
- есть понятная инструкция развертывания для Mac;
- данные можно экспортировать без зависимости от UI.
